# 서비스 디스커버리 (Service Discovery)

**서비스 디스커버리(Service Discovery)**는 클라우드 네이티브 환경에서 여러 마이크로서비스가 서로를 **자동으로 탐색하고 통신**할 수 있도록 하는 기술입니다. 서비스 디스커버리는 각 서비스의 **동적 위치(IP 주소, 포트 등)**를 관리하여, **수동으로 서비스 위치를 지정할 필요 없이** 서비스 간의 통신을 자동화합니다. 이를 통해 **확장성**과 **가용성**을 높이고, 동적으로 변하는 클라우드 환경에서의 **유연한 통신**을 보장합니다.

## 왜 서비스 디스커버리가 필요한가?

마이크로서비스 아키텍처에서 서비스들은 독립적으로 배포되고 실행됩니다. 각 서비스는 새로운 버전이 배포되거나 장애가 발생할 경우 IP 주소와 포트가 동적으로 변할 수 있기 때문에, 서비스 간의 통신을 **정적으로 설정**하기 어렵습니다. 서비스 디스커버리는 이러한 문제를 해결하여, 서비스 간 **동적 통신**을 가능하게 합니다.

## 서비스 디스커버리의 종류

서비스 디스커버리는 크게 **클라이언트 사이드 디스커버리**와 **서버 사이드 디스커버리**로 나뉩니다.

### 1. **클라이언트 사이드 디스커버리 (Client-Side Discovery)**

클라이언트가 직접 서비스 레지스트리로부터 **서비스 목록**을 조회하고, 특정 서비스로의 요청을 **로드 밸런싱**하는 방식입니다.

- **동작 방식**:
  1. 서비스 레지스트리에서 서비스 목록을 조회.
  2. 서비스 인스턴스 중 하나를 선택하여 요청을 보냄.
  3. 클라이언트 자체에 로드 밸런싱 로직이 내장됨.
- **장점**:
  - 클라이언트가 직접 서비스를 조회하므로 **구현이 단순**함.
- **단점**:

  - 클라이언트에 로드 밸런싱 로직이 있어 **클라이언트가 복잡**해짐.
  - 여러 언어와 클라이언트 구현이 필요할 수 있음.

- **예**: Netflix OSS의 Eureka

### 2. **서버 사이드 디스커버리 (Server-Side Discovery)**

**로드 밸런서**가 서비스 레지스트리와 통신하여, 클라이언트의 요청을 적절한 서비스 인스턴스로 **전달**하는 방식입니다. 클라이언트는 로드 밸런서를 통해 요청을 전송하고, 로드 밸런서가 서비스 인스턴스를 선택하여 요청을 처리합니다.

- **동작 방식**:

  1. 클라이언트는 로드 밸런서에 요청을 보냄.
  2. 로드 밸런서가 서비스 레지스트리에서 서비스 목록을 조회.
  3. 적절한 서비스 인스턴스를 선택하여 요청을 전달.

- **장점**:

  - 클라이언트는 서비스 인스턴스를 직접 관리하지 않아도 됨.
  - 로드 밸런서에 로드 밸런싱 로직이 있어 **클라이언트는 단순**함.

- **단점**:

  - 로드 밸런서에 장애가 발생할 경우 전체 서비스에 영향을 줄 수 있음.

- **예**: AWS ELB, NGINX, HAProxy

## 서비스 디스커버리의 구성 요소

### 1. **서비스 레지스트리 (Service Registry)**

서비스 레지스트리는 서비스의 **위치(IP 주소, 포트)** 정보를 저장하고 관리하는 데이터베이스입니다. 서비스 인스턴스가 시작되거나 종료될 때 해당 정보를 **자동으로 등록**하고 삭제합니다. 서비스 레지스트리는 서비스 디스커버리의 **중앙 데이터베이스** 역할을 하며, 모든 서비스가 이를 통해 서로의 위치를 탐색합니다.

- **주요 기능**:

  - 서비스 등록(Register): 서비스가 시작될 때 레지스트리에 자신의 위치를 등록.
  - 서비스 해제(Deregister): 서비스가 종료되거나 장애가 발생하면 레지스트리에서 위치 정보 삭제.
  - 서비스 조회(Lookup): 다른 서비스가 통신을 하기 위해 서비스 위치를 조회.

- **대표 도구**: Consul, Etcd, Zookeeper, Eureka

### 2. **서비스 제공자 (Service Provider)**

서비스 제공자는 네트워크를 통해 자신의 위치 정보를 **서비스 레지스트리**에 등록하는 역할을 합니다. 서비스 제공자가 시작되면 자신의 **IP 주소와 포트 번호**를 서비스 레지스트리에 등록하여 다른 서비스가 이를 찾을 수 있게 합니다.

- **예**: 마이크로서비스 인스턴스(애플리케이션 서버)

### 3. **서비스 소비자 (Service Consumer)**

서비스 소비자는 **서비스 레지스트리**에서 제공자의 위치를 조회하고, 그 정보를 바탕으로 다른 서비스에 요청을 보내는 역할을 합니다. 서비스 소비자는 동적으로 변하는 서비스의 위치를 실시간으로 조회하여 통신을 수행합니다.

- **예**: 다른 마이크로서비스, 프론트엔드 애플리케이션

## 서비스 디스커버리의 주요 기능

### 1. **동적 스케일링 지원**

클라우드 환경에서 서비스 인스턴스는 동적으로 **추가되거나 제거**될 수 있습니다. 서비스 디스커버리는 이러한 동적 스케일링 상황에서 서비스 위치를 **자동으로 업데이트**하여, 트래픽을 새로 추가된 인스턴스로 라우팅할 수 있도록 보장합니다.

### 2. **장애 감지 및 복구**

서비스가 비정상적으로 종료되거나 장애가 발생할 경우, 서비스 디스커버리는 해당 서비스의 정보를 **자동으로 제거**하여 더 이상 장애가 발생한 서비스로 트래픽을 보내지 않도록 합니다.

### 3. **서비스 헬스 체크**

서비스 디스커버리는 주기적으로 각 서비스의 **헬스 체크**를 수행하여 서비스가 정상적으로 작동하는지 확인합니다. 헬스 체크에 실패한 서비스는 레지스트리에서 제거됩니다.

### 4. **로드 밸런싱**

서비스 디스커버리는 서비스 간의 트래픽을 **균등하게 분배**하는 로드 밸런싱 기능을 제공합니다. 이는 서비스의 가용성과 성능을 높이는 데 중요한 역할을 합니다.

## 대표적인 서비스 디스커버리 도구

### 1. **Consul**

- HashiCorp에서 제공하는 서비스 디스커버리 도구로, **서비스 레지스트리**, **헬스 체크**, **키-값 스토어** 등을 지원합니다.
- 마이크로서비스의 위치를 자동으로 등록하고 조회할 수 있으며, 복잡한 네트워크 구성을 관리하기 용이합니다.

### 2. **Eureka**

- Netflix에서 개발한 서비스 디스커버리 도구로, 주로 **Spring Cloud**에서 사용됩니다.
- 클라이언트 사이드 디스커버리를 지원하며, **마이크로서비스의 동적 확장**에 적합합니다.

### 3. **Etcd**

- 분산형 키-값 저장소로, Kubernetes에서 **서비스 디스커버리와 설정 관리**에 사용됩니다.
- 매우 빠른 읽기/쓰기 성능과 데이터 일관성을 보장합니다.

### 4. **Zookeeper**

- Apache에서 제공하는 **분산 시스템을 위한 코디네이션 서비스**로, 서비스 디스커버리와 구성 정보를 관리합니다.
- 복잡한 분산 환경에서의 구성 관리 및 동기화 작업을 돕습니다.

## 서비스 디스커버리의 장점

1. **동적 확장 지원**: 서비스 인스턴스가 동적으로 변경되더라도 자동으로 인식하고 서비스 간 통신을 보장합니다.
2. **가용성 향상**: 장애가 발생한 서비스로의 트래픽을 자동으로 차단하여, 시스템 가용성을 높입니다.
3. **유연성**: 클라우드 환경에서 서비스 위치가 자주 변하는 상황에서도 유연하게 대응할 수 있습니다.
4. **운영의 단순화**: 수동으로 서비스 위치를 관리할 필요가 없어, 운영 복잡성을 줄일 수 있습니다.

---

서비스 디스커버리는 클라우드 네이티브 환경에서 **마이크로서비스 간의 동적 통신**을 지원하고, 서비스의 **가용성**과 **확장성**을 보장하는 핵심 기술입니다. 이를 통해 서비스 간의 연결을 자동으로 관리하고, 클라우드 환경에서의 복잡한 네트워크 구성을 효율적으로 처리할 수 있습니다.
